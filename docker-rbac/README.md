# Local RBAC/MDS test broker

A minimal, real Confluent Platform broker with RBAC and MDS enabled, in
Docker, for testing `targets/cp_mds.py` / `apply_to_mds.py` against the
actual API instead of only `../mock_server.py`. Single container: one
`confluentinc/cp-server` node running combined KRaft broker+controller, a
FILE-based MDS user store (no LDAP), and a locally-generated token-signing
keypair. No Schema Registry, Connect, ksqlDB, Control Center, or second
broker -- none of that is load-bearing for RBAC/MDS itself.

This has been run and passes end to end (see `test_rbac.sh`), for **both**
sources this repo supports: `../examples/cc-acls.yaml` fed directly into
`acl_to_rolebindings.py --target cp-mds` → `apply_to_mds.py --apply`, and
`../examples/ranger-kafka-policies.json` fed through
`export_ranger_policies.py` first. After applying, `test_rbac.sh` also
reads every binding back from MDS itself (`verify_bindings.py`, using
MDS's own lookup endpoints) rather than trusting `apply_to_mds.py`'s 204
status codes alone -- this is a real check: pointed at a binding that was
never applied, it fails with `expected role 'DeveloperRead' not found in
MDS lookup []`. It's still a single-node, file-user-store, no-TLS setup,
so treat it as "the wire format really works for both sources," not as a
substitute for testing against your actual production-shaped MDS
deployment (LDAP, mTLS, multiple brokers) before trusting this in a real
migration.

## Quick start

```bash
cd docker-rbac
./test_rbac.sh            # generates the keypair if missing, starts the broker,
                           # sanity-checks both MDS bind endpoints with curl,
                           # runs the real pipeline against it, tears down
./test_rbac.sh --keep     # same, but leaves the broker running afterward
```

## Manual use

```bash
./gen-keypair.sh           # once, or whenever you delete secrets/
docker compose up -d
curl -u mds:mds1 http://localhost:8090/security/1.0/authenticate   # -> {"auth_token": "...", ...}

# from the repo root (CLUSTER_ID defaults to the one baked into docker-compose.yml):
CLUSTER_ID=Y0TWB4uSQfO0oZyvyng4Yw
python3 acl_to_rolebindings.py examples/cc-acls.yaml --target cp-mds \
  --kafka-cluster-id "$CLUSTER_ID" --cluster-role ClusterAdmin -o rb.yaml
MDS_USERNAME=mds MDS_PASSWORD=mds1 python3 apply_to_mds.py rb.yaml \
  --apply --mds-url http://localhost:8090

docker compose down -v      # when done
```

## How it's wired

* **No ZooKeeper, no LDAP.** KRaft (`KAFKA_PROCESS_ROLES=broker,controller`) removes the ZK dependency; `confluent.metadata.server.user.store=FILE` (`login.properties`) removes the LDAP dependency. `mds` is a `super.user`, so it can create role bindings for everyone else without needing a role binding of its own.
* **`secrets/tokenKeypair.pem` / `tokenPublicKey.pem`** (generated by `gen-keypair.sh`, gitignored) are the RSA keypair MDS uses to sign/verify its bearer tokens (`confluent.metadata.server.token.key.path`). A Kafka client authenticating with a bearer token instead of a username/password does so on the `TOKEN` listener (port 9092, `SASL_PLAINTEXT`/`OAUTHBEARER`, verified with the public key) -- required for the broker to start with RBAC configured, even though this test only exercises the REST side (port 8090).
* **`login.properties`** is the FILE user store: one `username:password` per line, **no comments allowed** -- the parser rejects any line that isn't exactly `user:password`, which is why this file has no header comment (documented here instead).
* **`CLUSTER_ID`** (defaulted in `docker-compose.yml`, overridable via env var) is a KRaft cluster ID generated once with `docker run --rm confluentinc/cp-server:8.1.0 kafka-storage random-uuid`; regenerate it (`CLUSTER_ID=... docker compose up -d`) if you ever need a fresh cluster.
* **MDS's two role-binding endpoints**, both exercised by `test_rbac.sh`:
  * `POST /security/1.0/principals/{principal}/roles/{roleName}` with `{"clusters": {...}}` for a cluster-scoped role (e.g. `ClusterAdmin`) -- no `resourcePatterns`, and MDS 400s if you send one that needs resources here (try `ResourceOwner` this way and it'll tell you: `"Resources must be specified for role ResourceOwner"`).
  * `POST /security/1.0/principals/{principal}/roles/{roleName}/bindings` with `{"scope": {...}, "resourcePatterns": [...]}` for a resource-scoped role.

  This matches `targets/cp_mds.py`'s `cluster_binding()` vs. `locator_for()` split exactly.
* **MDS's read side**, used by `verify_bindings.py`, is two different lookup endpoints (neither takes a `"scope"` wrapper -- just a bare `{"clusters": {...}}` body, unlike the write endpoints):
  * `POST /security/1.0/lookup/principals/{principal}/roleNames` -> `["DeveloperRead", ...]`, the role names bound to that principal at that scope.
  * `POST /security/1.0/principals/{principal}/roles/{roleName}/resources` -> `[{"resourceType", "name", "patternType"}, ...]`, the resource patterns bound under that role.
* **Single-node replication factors.** cp-server enables several internal topics/features by default with replication factor 3, which one broker can never satisfy: `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR`, `KAFKA_CONFLUENT_METADATA_TOPIC_REPLICATION_FACTOR`, `KAFKA_CONFLUENT_LICENSE_TOPIC_REPLICATION_FACTOR`, `KAFKA_CONFLUENT_TIER_METADATA_REPLICATION_FACTOR`, `KAFKA_CONFLUENT_BALANCER_TOPIC_REPLICATION_FACTOR`, and `KAFKA_CONFLUENT_CLUSTER_LINK_METADATA_TOPIC_REPLICATION_FACTOR` are all set to 1. One is deliberately left alone: `confluent-audit-log-events`' replication factor is a JSON-blob property (`event.logger.exporter.kafka.topic.config`), and the broker already self-heals it (tries 3, fails twice, falls back to 1, succeeds, never recurs) -- overriding it would trade a harmless two-line startup blip for the risk of getting that JSON wrong.
